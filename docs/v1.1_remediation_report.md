# PredicateLab V1.0 → V1.1 remediation report

Date: 2026-11-01.  Scope: scientific trustworthiness and execution reliability
of the existing PredicateLab workspace.  This report records what was changed,
what was actually executed, and what remains unproven.

Status vocabulary used throughout:

* **VERIFIED** — executed in this workspace and checked against an observable
  result.
* **CODE_ONLY** — implemented and covered by tests, but the real target path was
  not executed in this phase.
* **NOT_VERIFIED** — no evidence; must not be presented as a result.
* **FAILED** — an observed defect or an unsupported claim.  A fixed defect is
  marked "FAILED → fixed".

## 1. Repository state and change boundary

At the start of the work the tree was already dirty.  All existing
modifications were preserved; nothing was reset, cleaned or overwritten.
`git status` at the end still shows the original modified files plus the new
modules, tests, configs and documents.

New core modules:

* `predicatelab/core/holdout.py` — global holdout ledger and claim rules;
* `predicatelab/core/identity.py` — content manifest, hashing, atomic writes,
  strict JSON, code/environment fingerprints;
* `predicatelab/core/label_window.py` — label-dependency parsing and time
  isolation.

Main modified modules: `core/engine.py`, `core/store.py`, `core/schema.py`,
`core/protocol.py`, `core/adapter.py`, `cli.py`, the TSIL and tabular
adapters/generators/worker, and the quick/smoke/full configs.

The real SQLite database was migrated in place after taking a byte-for-byte
backup.  The historical TSIL holdout was **not** re-run.  No new run directory
was created under `artifacts/` after 2026-10-31: the latest real run remains
`run_20261031_153702`.

## 2. What was wrong in V1.0

The V1.0 failure modes that motivated this remediation:

1. holdout access was keyed by run/candidate metadata, so a new run id could
   read the same data again; no global consumed record existed;
2. label dependency was handled by calendar-day assumptions; 2023-12-28/29
   labels depended on January 2024 prices but could remain in the 2023
   confirmation/validation tail;
3. cache identity did not include the full data content, label spec, phase,
   seed or code environment; phase workdirs could collide;
4. a round could be marked complete without committed evidence/feedback;
   partial-fold failures and non-finite numbers could still yield "success";
5. discovery "validated" was readable as independent confirmation; historical
   rows could be silently upgraded.

## 3. Fixes and evidence

### 3.1 One-time holdout ledger — VERIFIED

`core/holdout.py` and `store.claim_holdout` implement:

* a global, data-only `holdout_key` (dataset, snapshot, full data manifest,
  label spec, test window); run/candidate/protocol are absent;
* atomic claim under `BEGIN IMMEDIATE`, with a partial unique index over
  consumed statuses;
* `claimed/running/completed/failed/interrupted` all count as consumed; a crash
  cannot be laundered into a fresh slot;
* exact retry of `(run_id, candidate_id, manifest_hash)` reuses the row;
  completed retries return the saved result and add no second claim;
* `exploratory_reuse` rows are recorded separately and never confirmatory;
* a period-level overlap guard rejects a new identity for the same dataset and
  overlapping dates; `legacy_unknown` windows match everything and fail closed.

Tests: `tests/test_adversarial_holdout.py` (10 tests), including a concurrent
two-writer race (exactly one winner), crash-then-retry, failed-not-reclaimable,
exploratory reuse, overlapping legacy window, unknown legacy window and a
non-overlapping allowed window.

Real database: 2 historical holdout accesses were backfilled as
`origin=backfill_legacy`, `status=completed`; the TSIL row has
`test_start=2024-01-01`, `test_end=2025-08-31`; the tabular row has
`legacy_unknown` dates and `missing_fields=["test_start","test_end"]`.  A guard
test on a copy of the migrated database confirmed that:

* a new V1.1 TSIL claim for 2024-01-01..2025-08-31 is blocked with an
  "overlaps an already-consumed holdout" error even though the snapshot
  identity differs;
* the tabular dataset is blocked because its legacy window is unknown.

This is the intended fail-closed behaviour.

### 3.2 Label-dependency time isolation — VERIFIED

`core/label_window.py`:

* parses `future_offset_trading_days` from the label expression and compares it
  with the `DataContract.label_dependency` declaration; a mismatch raises;
* uses the adapter's real trading calendar;
* trims the tail of train/validation/test whose labels require prices that do
  not exist inside the fold, and writes the trimmed end into the effective fold
  (the earlier version only reported it);
* rejects `purge_days=0` for label-dependent folds;
* records the exact leaked `(instrument, date)` count at a declared boundary;
* a validation segment reaching into holdout dates is a hard error.

Tests: `tests/test_adversarial_label_isolation.py` (6 tests), including the
real qlib calendar/data assertion: 2023-12-28 and 2023-12-29 each have 300
CSI300 instruments → **600 leaked sample-dates** exactly (314 instruments in
the union).  Effective folds were confirmed to trim to 2023-12-27 for
confirmation/holdout validation and 2023-12-25 for the train tail in the
synthetic case.

Config validation on the real data reports
`label_offset_trading_days=2`, expression
`Ref($close, -2) / Ref($close, -1) - 1`, and `label_isolation.ok=true` for all
TSIL configs.  The full content manifest hash is
`f08db16ec995bf73466511c68b22b221e29035624b07055cf64d08e51f8772f5`.

### 3.3 Complete cache identity — VERIFIED

`core/identity.py` and the trial hash include: full data content Merkle root,
snapshot, label expression/spec, fold dates and role, phase, seed, model spec,
training budget, preprocessing version, code fingerprint (commit + dirty
fingerprint) and environment versions.  Attempt counters and workdir paths are
deliberately excluded so a retry can reuse the same scientific identity.

The TSIL snapshot now hashes every feature file plus calendar and instrument
files, replacing the V1.0 sampled 8-file hash.  The persisted cache is accepted
only if its own `manifest_hash` validates; a tampered cache is rebuilt.

Tests: `tests/test_adversarial_identity.py` (18 tests) cover sensitivity to
phase, seed, snapshot, data manifest, label spec/expression, preprocessing,
model, code and environment; fold hashes; full-content change detection;
tampered cache rejection; corrupt cached trial; missing prediction; and failed
trials never cached.

Measured cost of a cached TSIL `validate-config`:
**27.6 s**, peak RSS **~591 MB**.  A cache miss re-hashes the full store.

### 3.4 Run/round state machines and execution reliability — VERIFIED

* run statuses `running → search_complete → confirmation_complete →
  final_complete`, failure `interrupted/failed/final_failed`;
* a round becomes `completed` only after evidence, feedback and status commit;
* interrupted rounds resume the persisted proposal set rather than generating
  new candidates;
* trial/evidence writes are atomic (temp file + replace);
* a nonzero worker exit is authoritative even when a success-shaped
  `result.json` exists; the stale result file is removed before each attempt;
* malformed or NaN/Inf worker output is `failed`;
* NaN/Inf in stored statistics becomes `null` plus `null_paths`;
* partial-fold coverage below the threshold is `insufficient`;
* multi-seed runs persist the seed on every trial/attempt and use
  phase/fold/seed-isolated workdirs.

Tests: `tests/test_adversarial_engine.py` (10 tests) and
`tests/test_adversarial_worker.py` (6 tests).  The dev end-to-end run
(`run_20261101_042749`) persisted 103 trials across `screen/full/confirmation/
final` with seeds 2025/2026/2027 and a single completed round.

### 3.5 Stage separation and candidate states — VERIFIED on dev data

`finalize` now refuses, in order: an unfinished run; a candidate without
discovery evidence; an unfrozen family; a candidate outside the frozen family;
snapshot drift; and missing confirmation.  Confirmation evaluates the frozen
family only and never feeds the generator.  Candidate states distinguish
`exploratory_positive`, `resampling_confirmed`, `independently_confirmed`,
`insufficient`, `rejected` and `legacy_unknown`.

Tests: `tests/test_adversarial_engine.py` covers all refusal paths,
idempotent repeated finalize, resume without duplicate evidence, interrupted
round rerun, multi-seed execution and aggregate non-finite errors.

### 3.6 Evidence bundle — FAILED → fixed, VERIFIED on dev data

The dev end-to-end run exposed a real export defect: a trial with an empty
`predictions_path` yields `Path("")`, which exists (the current directory), so
export tried to copy `.` and crashed with `IsADirectoryError`.  Two tests were
written first in `tests/test_adversarial_export.py`; both failed; the export
was then fixed to:

* skip empty/non-file prediction paths;
* count them as `predictions.n_missing`;
* copy real files into `predictions/` and include them in `checksums.sha256`;
* record `predictions.n_copied/n_missing/files` in `bundle_manifest.json`.

The tabular adapter was also extended to write `sample`, `score` and `label`
arrays when `save_predictions` is enabled; TSIL already writes `instrument`,
`date`, `score`, `label`.  All existing configs now set
`search.save_predictions: true`.

Dev bundle result: `n_copied=103`, `n_missing=0`, zero checksum mismatches,
`bundle_hash=ecfe6973bff39f3b283be9571d6b807dc5e38c084ad87c2c5dc29df0f9039796`.
The first dev run (`run_20261101_042449`) is retained as the pre-fix record;
its bundle shows `n_missing=103`, which is exactly the defect the fix removes.

## 8. Remaining risks

1. **TSIL V1.1 path is not exercised on real data.**  The TSIL adapter changes
   (full manifest, effective folds, worker result handling, prediction npz) are
   covered by unit tests and `validate-config`, but no V1.1 discovery or
   confirmation run has been executed.  GPU 0–7 were at 99 % utilisation during
   this phase; the smoke run remains an approval-gated next step on 2018–2023
   only.
2. **Full content manifest cost.**  A cached TSIL validation takes ~27.6 s and
   ~591 MB; a cache miss re-hashes the whole feature store.  On a larger store
   this may become a practical bottleneck.  The cache is self-validating, so
   this is a performance risk, not a correctness one.
3. **Static tabular windows are empty.**  The period-level guard cannot use
   dates, so tabular confirmation reuse protection relies on the snapshot hash
   of the full feature matrix/labels.  Changing the snapshot without changing
   the data would need an explicit exploratory reuse record.
4. **Legacy rows block reuse by design.**  The tabular legacy holdout has
   unknown dates, so a fresh confirmatory claim on the same dataset in the real
   database is refused.  This is fail-closed and intended; an analysis must use
   `exploratory_reuse` or a fresh database.
5. **Mechanical status versus scientific state.**  `finalize` returns
   `status=success` when execution completed; the scientific state is in
   `result.state`.  Consumers must read the state and `null_paths`, not the
   top-level status.
6. **Resampling is not independent replication.**  The tabular confirmation is
   `resampling_confirmed`; only a time-forward confirmation may claim
   `independently_confirmed`.
7. **Historical artifacts remain as recorded.**  No historical report,
   `final_evaluation` or `frozen_manifest` was rewritten.  Their labels are
   `legacy_unknown`; they are not V1.1 evidence.
8. **No new TSIL numbers exist.**  Any claim about the effect of predicates on
   the 2024–2025 holdout remains the V1.0 single evaluation (IC effect
   −0.00103, p=0.386) and must be read as an unconfirmed historical result, not
   as a V1.1 finding.
