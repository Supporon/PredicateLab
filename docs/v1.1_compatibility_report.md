# PredicateLab V1.1 compatibility report

This report describes what V1.1 keeps compatible, what it intentionally
changes, and how to migrate safely.  "Compatible" means an existing invocation
or database still works; it does not mean old scientific conclusions carry
over.

## 1. CLI compatibility

### 1.1 Existing commands

| command | status | notes |
|---|---|---|
| `domains` | unchanged | same output shape |
| `validate-config` | compatible, but stricter | now also reports full data manifest, label isolation, effective folds, seeds and suitability; exits `2` on a protocol/label/suitability blocker |
| `discover` | compatible | same flags `--config --rounds --run-id --db`; resuming a finished run no longer duplicates evidence or rounds |
| `report` | compatible | reads the run and rewrites `report.json` / `report.md` |
| `evidence` | compatible | same table output; extra `stage`/`state` values may appear |
| `examples` | unchanged | mineral/image contracts only |
| `export` | compatible, fixed | now skips unusable prediction paths, counts missing predictions and adds them to checksums |
| `finalize` | **behaviour-changing** | now requires `search_complete` and confirmation; a V1.0-style direct finalize of a `validated` candidate is refused |

### 1.2 New commands

| command | purpose |
|---|---|
| `freeze-family` | persists the exact discovery family and its manifest hash |
| `confirm` | evaluates only the frozen family on confirmation folds |
| `migrate` | opens/upgrades the SQLite schema additively; optional `--backfill-artifacts` |
| `holdout-audit` | lists the global holdout ledger; reads no data |

New flags are additive (`--candidate-id` on freeze/confirm, `--db` on export,
`--backfill-artifacts` on migrate).

### 1.3 Exit codes and errors

* `0` — the requested action completed; scientific state is reported in the
  payload (`result.state`), not by the exit code.
* `2` — config/protocol/confirmation/finalize blocker.  The message is printed
  to stderr prefixed with `finalize blocked:`, `confirmation blocked:` or
  `freeze blocked:`.
* A `HoldoutConsumed` error is surfaced through the same blocker path; it is
  never downgraded to a warning.

Scripts that treated exit code `0` as "scientifically confirmed" must now read
`result.state` (`independently_confirmed` / `resampling_confirmed` /
`insufficient` / ...).

## 2. Config compatibility

Existing config keys are still read by the same pydantic models.  New optional
keys:

* `seeds: [...]` — per-seed execution; defaults to `[training.seed]`;
* `protocol.confirmation_folds` / `protocol.confirmation_kind` — required in
  practice for `confirm`; `resampling` is explicit;
* `search.save_predictions` — default `false`; all shipped configs set `true`;
* `search.min_fold_coverage`, `min_seed_agreement` — coverage/seed gates;
* `data.label_dependency` / `DataContract.label_dependency` — declared label
  offset; TSIL declares `future_offset_trading_days: 2`;
* `run.require_confirmation` — already present; a `true` value is now enforced
  with real gates.

Intentional config-level break:

* A TSIL config that keeps the old fold layout (for example putting `f2023`
  into `search.screen_folds`) now fails validation with "policy references
  unknown discovery folds".  The shipped configs were moved to search folds
  `f2020`–`f2022` and confirmation fold `f2023` (time-forward), with the
  holdout `2024–2025` untouched.

All shipped configs validate:

```
configs/tsil_lstm_smoke.yaml   rc=0
configs/tsil_lstm_quick.yaml   rc=0
configs/tsil_lstm_full.yaml    rc=0
configs/tabular_quick.yaml     rc=0
configs/tabular_dev_v11.yaml   rc=0
```

## 3. Database compatibility

### 3.1 Schema changes are additive

New tables: `schema_migrations`, `trial_attempts`, `frozen_families`,
`holdout_access`, `holdout_access_events`.

New columns (with defaults, so old rows remain readable):

* `runs`: `stage`, `snapshot_hash`, `protocol_hash`, `code_fingerprint`,
  `updated_at`;
* `rounds`: `status`, `status_origin`, `error`, `started_at`, `ended_at`;
* `trials`: `phase`, `seed`, `snapshot_hash`, `identity_hash`, `attempt`,
  `result_hash`, `predictions_sha256`, `null_paths`, `started_at`,
  `finished_at`;
* `trial_attempts`: `seed`;
* `evidence`: `stage`, `state`, `seed`;
* `final_evals`: `run_id`, `holdout_key`, `access_id`, `stage`, `state`,
  `exploratory`, `result_hash`.

New indexes: `ux_evidence_stage` (unique per run/round/candidate/stage, partial),
`ux_holdout_active` (one consumed holdout per key).

No column is dropped, renamed or rewritten.  No historical artifact is deleted.

### 3.2 Direction of compatibility

* **V1.1 code on a V1.0 database**: supported and verified.  Opening the
  database migrates it in place to schema version 3.
* **V1.0 code on a V1.1 database**: not supported.  The old code does not know
  `schema_migrations`, the new columns or the ledger and may produce an
  inconsistent scientific state.  Use the backup if V1.0 behaviour is needed.
* **V1.1 code on a V1.1 database**: idempotent; reopening adds no migration
  row.

### 3.3 Legacy rows

Unprovable fields are labelled, never fabricated:

* trials: `phase=legacy_unknown`, `seed=NULL`;
* rounds: `status=legacy_unknown`, `status_origin=legacy` when no feedback
  proves completion, otherwise `completed/backfill_feedback`;
* evidence: `stage=legacy`; a V1.0 `validated` row becomes
  `exploratory_positive`, never `independently_confirmed`;
* final evaluations: `stage=legacy`, `state=legacy_unknown`, with an explicit
  note;
* holdout rows: `origin=backfill_legacy`; missing snapshot/test fields become
  `legacy_unknown` and are listed in `details.missing_fields`.

Consequences:

* Legacy trials are re-executed rather than trusted.  A missing prediction file
  or digest never marks a legacy row "corrupt"; it is simply not cacheable.
* A legacy holdout row with unknown dates blocks every future confirmatory
  claim on the same dataset (fail closed).  A deliberate re-analysis must use
  `exploratory_reuse` and is labelled as such.

### 3.4 Migration procedure (verified on the real database)

```bash
PY=/home/dmz-ai/miniconda3/envs/zzr_py312/bin/python

# 1. back up byte-for-byte (already done: artifacts/predicatelab.sqlite.v1.0-backup-20261101.sqlite)
cp artifacts/predicatelab.sqlite artifacts/predicatelab.sqlite.bak

# 2. migrate and backfill
$PY -m predicatelab.cli migrate --db artifacts/predicatelab.sqlite \
    --backfill-artifacts artifacts

# 3. inspect
$PY -m predicatelab.cli holdout-audit --db artifacts/predicatelab.sqlite
sqlite3 artifacts/predicatelab.sqlite \
  "select version,description from schema_migrations order by version;"

# 4. test on the migrated copy, never by re-reading data
$PY -m pytest tests/test_migration.py -q
```

Rollback is restore-only: stop all processes, copy the backup over the
database, and do not use V1.0 code with a V1.1 artifact directory.  There is no
down-migration because deleting columns could destroy history; that would
violate the preservation requirement.

### 3.5 Verified real-database outcome

* backup SHA-256 `6facc4ad…`, migrated database SHA-256 `ba08e385…`;
* schema version 3, migration rows `[2,3]`;
* rows preserved: 19 tasks, 2 snapshots, 74 templates, 74 candidates,
  269 fitted instances, 12 runs, 17 rounds, 519 trials, 206 evidence rows,
  15 feedback rows, 2 final evaluations;
* 2 holdout rows backfilled, both `completed`, `origin=backfill_legacy`;
  TSIL window `2024-01-01..2025-08-31`, tabular window `legacy_unknown`;
* a claim on a copy of the migrated database for the TSIL 2024–2025 window is
  blocked by the overlap guard even with a different snapshot identity, and
  the tabular dataset is blocked by its unknown window.

## 4. Artifact compatibility

New or changed files in a run directory:

| file | compatibility |
|---|---|
| `context.json` | same name; new keys (`data_manifest_hash`, `label_isolation`, effective folds, code/environment).  Old keys retained. |
| `report.json` / `report.md` | same names; evidence counts may include new stages/states |
| `evidence.jsonl` | same name; rows gain `stage`/`state` |
| `frozen_manifest.json` | same name; now written only after freeze/finalize |
| `frozen_family.json` | new; required for confirmation/finalize |
| `confirmation.json` | new; confirmation results |
| `final_evaluation.json` | same name; result now carries `state`, `null_paths`, seed/fold decompositions |
| `bundle/` | new; checksums, bundle manifest, predictions |

Old artifact directories are untouched.  `export` can bundle a historical run
if its adapter data is still available, but historical rows remain
`legacy_unknown` and missing predictions are counted, not invented.

## 5. Python API compatibility

* `PredicateLabEngine(config, db_path=None, run_id=None)` unchanged.
* `engine.run(rounds=...)` unchanged; adds resume semantics.
* `engine.finalize(candidate_id)` unchanged in signature, stricter in
  preconditions and richer in output.
* `finalize_run(config, run_id, candidate_id, db_path=None)` unchanged.
* New: `freeze_family(...)`, `confirm(...)`, `export(...)`.
* `StateStore` gains ledger/state methods; `schema_version` reports 3.
* `TrialRequest` gains phase/seed/identity/label fields with defaults, so
  custom adapters that only implement the V1.0 attributes still construct.

Custom adapters that return a trial dict without `predictions_path` remain
valid: export counts the missing file.  Adapters that want prediction
artifacts should honour `request.save_predictions` and write a file into
`request.workdir`.

## 6. Behavioural compatibility matrix

| situation | V1.0 | V1.1 |
|---|---|---|
| new run id reads same holdout | allowed | blocked (`HoldoutConsumed`) |
| crash during finalize | could retry as fresh | counts as consumed; only exact retry allowed |
| completed finalize retried | could duplicate | returns saved result, one ledger row |
| legacy holdout with unknown dates | ignored | blocks same dataset, fail closed |
| validated discovery candidate | could be finalized | must be frozen and confirmed first |
| single-point holdout CI | stored NaN / treated as success | `null` + `null_paths`, state `insufficient` |
| partial fold failures | could still aggregate as success | coverage below threshold → `insufficient` |
| NaN/Inf result | could be cached as success | sanitised to null or `failed` |
| worker rc≠0 with result.json | result could be used | authoritative `failed` |
| 2023-12-28/29 labels in 2023 tail | could leak | trimmed using the real trading calendar |
| trial cache identity | protocol + config only | full data/label/fold/phase/seed/model/code/env |
| phase workdirs | shared | phase/fold/seed isolated |

## 7. What is not compatible, by design

1. **Scientific claims.**  V1.0 `validated` means "passed the search-fold
   bar", not "independently confirmed".  Historical rows cannot be upgraded.
2. **Reuse of the 2024–2025 TSIL holdout.**  It is consumed.  There is no
   compatibility path that makes it fresh again.
3. **Direct finalize.**  A V1.0 script that called `finalize` immediately after
   `discover` must now call `freeze-family` and `confirm` first, or it will
   exit `2`.
4. **Old TSIL discovery folds.**  Configs that searched on 2023 must move the
   search/validation folds earlier; otherwise validation fails closed.
5. **Tabular confirmatory reuse in the migrated real DB.**  The legacy tabular
   row has unknown dates, so the dataset is blocked for fresh confirmatory
   access.  Use a fresh database for a new study, or record exploratory reuse.

## 8. Compatibility verification performed

* all five shipped configs pass `validate-config` (rc=0);
* the real database was migrated with a backup and row-count comparison;
* `tests/test_migration.py` starts from an exact V1.0 schema, asserts
  preservation, idempotence and legacy labelling;
* CLI commands `discover → freeze-family → confirm → finalize → export` were
  executed end to end on the dev tabular configuration
  (`run_20261101_042749`);
* `export` was exercised with zero predictions, missing predictions and
  directory paths; checksums were recomputed independently;
* no V1.0 artifact or report was overwritten.

Residual compatibility risks are listed in
[the remediation report](v1.1_remediation_report.md#8-remaining-risks):
TSIL V1.1 has not been executed on real data, the tabular window guard is
empty, and the content-manifest validation is comparatively expensive.

The TSIL V1.1 path was subsequently fixed and covered by synthetic
unit/integration tests (see [the audit fix report](v1.1_fix_report.md)), but
that does **not** upgrade it to a verified integration: no real qlib/TSIL
training run, no GPU run, and no cross-process crash recovery have been
performed.  Real TSIL integration remains `NOT_VERIFIED` /
`BLOCKED_RESOURCE`.
